# API and Security Integration

## Trust boundaries

```text
X content script and extension UI
        │ chrome.runtime messages
        ▼
Extension service worker ── HTTPS ── TradeTag gateway
        │                                  │
        │ local wallet provider            └── signed Binance Web3 API requests
        ▼
Wallet extension installed by the user
```

The extension is a public, inspectable client. Any API secret stored in its files, configuration, or extension storage can be extracted. Binance Web3 API request signatures are generated by the gateway using product credentials held on the server; these credentials must never be included in the extension package.

The public preview includes a gateway client token. It is extractable and must be treated as a public identifier, not a secret. The gateway applies per-IP and global rate limits. Never reuse a Binance product API secret as the gateway token.

TradeTag does not access or persist login credentials, private keys, recovery phrases, or wallet signatures. Binance Web3 API requires the public `userWalletAddress` to build a wallet-specific swap transaction. The gateway temporarily forwards that address to Binance and does not log or store it.

## Gateway routes

- `GET /v1/token/search`
- `GET /v1/market/token-info`
- `GET /v1/market/candles`
- `GET /v1/trade/quote`
- `GET /v1/trade/swap`
- `GET /v1/trade/approve`

The public preview has its gateway address and public client token preconfigured. Private deployments should use a separate gateway credential. Users do not configure an RPC endpoint; the wallet uses its own default RPC.

The gateway must keep the upstream host and allowed Binance paths fixed. Validate parameter lengths, chain IDs, token addresses, and amounts. Do not accept arbitrary upstream URLs, arbitrary Binance paths, or client-provided signature headers.

## Binance Web3 API

Official documentation: <https://web3.binance.com/en/dev-docs>

API paths use `https://web3.binance.com/build` as their root, including:

- `GET /api/v1/dex/market/token/search`
- `GET /api/v1/dex/market/price`
- `GET /api/v1/dex/market/candles`
- `POST /api/v1/dex/market/token/basic-info`
- `POST /api/v1/dex/market/token/price-info`
- Aggregator quote, swap construction, and quote-and-swap endpoints

The gateway signs upstream requests with `X-OC-APIKEY`, `X-OC-TIMESTAMP`, and `X-OC-SIGN`. Solana uses chain ID `CT_501`. Quote IDs are short-lived; request a fresh quote before constructing a transaction.

## Wallet boundary

- Solana: use Binance Wallet's Wallet Standard `solana:signAndSendTransaction` feature when available. The wallet signs and broadcasts through its own default RPC.
- EVM: discover the Binance Wallet provider through EIP-1193 or EIP-6963, check the selected chain ID, and submit through the wallet's default RPC.
- Never read private keys, recovery phrases, or wallet storage.
- Present the network, asset, direction, amount, slippage, fees, and estimated output before the user confirms in the wallet.
- EVM token approval and swap are separate wallet-confirmed transactions.

- Binance API credentials remain in the server environment file and are excluded from the public source repository and extension ZIP.
